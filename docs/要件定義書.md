## 1. プロジェクト概要

### 1-1. 背景・目的

現状、仕事とプライベートのタスクが頭の中や紙のメモに散在しており、抜け漏れが発生しやすい状態にある。  
タスクを一覧で可視化できるWebアプリを作ることで、自己管理の効率化を図る。

また本プロジェクトは、アプリ開発の実務フロー（要件定義 → 設計 → 実装 → テスト）を体験することも目的とする。

### 1-2. アプリ概要

Trelloを参考にした、カードベースUIのスケジュール管理Webアプリを開発する。  
「リスト（カテゴリ列）」の中に「カード（タスク）」を配置し、ドラッグ&ドロップで状態を管理できるシンプルなツールを目指す。

### 1-3. 開発期間・フェーズ

| フェーズ | 内容 |
|---|---|
| 要件定義 | 何を作るかを決める（現在） |
| 設計 | 画面・データ構造を設計する |
| 実装 | コードを書く |
| テスト | 動作確認・修正 |

## 5. 受け入れ基準

<!-- 受け入れ基準 = 「この条件を満たしたら完成とみなす」というテスト基準。
     曖昧な「できる」だと、どこまで作れば完成なのかが分からなくなります。
     実務ではQAエンジニアがこれをもとにテストを設計します。 -->

| 機能 | 受け入れ基準（これを満たしたら完成） |
|---|---|
| F-1 カード作成 | ・「＋」ボタン等でカード作成フォームが開く<br>・タイトルを入力して保存すると、対象リストにカードが追加される<br>・タイトルが空のまま保存しようとすると、エラーまたは保存不可になる |
| F-2 カード編集 | ・カードをクリックすると編集モードになる<br>・タイトル・メモを変更して保存すると、カードの表示に反映される |
| F-3 カード削除 | ・削除ボタン押下で確認ダイアログが出る<br>・「OK」でカードが消える。「キャンセル」で元に戻る |
| F-8 D&D移動 | ・カードをドラッグして別リストにドロップすると、そのリストに移動する<br>・移動後もデータが正しく保存されている |
| F-9/F-10 保存・復元 | ・カード追加後にブラウザをリロードしても、カードが消えていない<br>・別タブで開くと同じデータが表示される |

## 7. データ要件

<!-- 何のデータをどんな形で保存するかを定義します。
     これを決めると、実装時にデータ構造（JavaScriptのオブジェクト設計）が明確になります。 -->

### 7-1. 保存するデータの種類

| データ名 | 説明 | 属性（プロパティ） |
|---|---|---|
| ボード | アプリ全体のデータ | リストの配列 |
| リスト | カードをまとめるカラム | id, タイトル, カードの配列 |
| カード | 1件のタスク | id, タイトル, メモ（任意） |

### 7-2. データ構造イメージ（JSON形式）

```json
{
  "lists": [
    {
      "id": "list-1",
      "title": "未着手",
      "cards": [
        { "id": "card-1", "title": "〇〇の資料作成", "memo": "金曜までに提出" },
        { "id": "card-2", "title": "〇〇に連絡", "memo": "" }
      ]
    },
    {
      "id": "list-2",
      "title": "完了",
      "cards": []
    }
  ]
}
```

### 7-3. 保存先

- **ブラウザのLocalStorage**（キー名: `schedule-app-data`）
- 注意: LocalStorageはブラウザ・PC単位のため、複数端末での共有は不可（スコープ外）

## 11. リスク

<!-- リスク = 「うまくいかないかもしれないこと」を事前に洗い出す。
     実務では影響度と発生確率で評価し、対策を考えます。 -->

| # | リスク内容 | 影響 | 対策 |
|---|---|---|---|
| R-1 | LocalStorageのデータがブラウザ設定でクリアされる | 全データ消失 | 利用前に「データはブラウザに依存する旨」をユーザーに周知（今回は自分のみのため許容） |
| R-2 | ドラッグ&ドロップの実装が複雑で時間がかかる | スケジュール遅延 | HTML Drag and Drop APIを使用し、まずシンプルな実装から始める |
| R-3 | 要件が曖昧なまま実装に進み手戻りが発生する | 手戻り・時間ロス | 本要件定義書でスコープを明確化し、設計フェーズで確認してから実装する |
| R-4 | JavaScriptの知識不足により、不具合発生時の原因特定が困難になる | 実装が止まる | 実装フェーズで小さな単位ごとに動作確認しながら進める。エラーメッセージの読み方も都度解説する |
